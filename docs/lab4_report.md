## 1. Оцінка архітектурних ризиків та компромісів (ATAM)

Для аналізу обрано два ключові сценарії якості системи **TechRepair Hub** із Лабораторної роботи №1 з урахуванням результатів попередніх лабораторних робіт.

### Сценарій 1: Відмовостійкість (Fault Tolerance)
*   **Опис із ЛР 1:** Збій зовнішнього сервісу (наприклад, модуля складу) під час узгодження вартості ремонту та списання деталей.
*   **Архітектурне рішення:** Впровадження патерна оркестрованої Saga із компенсаційними діями (реалізовано у ЛР 3).
*   **Виявлений ризик:** Помилка безпосередньо під час виконання компенсаційної команди (збій `release_parts`), що призводить до "зависання" зарезервованої деталі на балансі.
*   **Чутливий параметр (Sensitivity Point):** Надійність механізму збереження стану транзакції (State Machine) та черги повідомлень для автоматичних повторів (Retry).
*   **Точка компромісу (Trade-off):** *Надійність та узгодженість даних проти Складності системи*. Saga гарантує цілісність даних між доменами, але суттєво ускладнює код та підтримку порівняно зі звичайною локальною транзакцією.

### Сценарій 2: Продуктивність (Performance)
*   **Опис із ЛР 1:** Пікове навантаження (100+ одночасних клієнтів перевіряють статус своїх заявок за QR-кодом; цільовий показник p95 < 500 мс).
*   **Архітектурне рішення:** Ізоляція піддоменів (Core та Warehouse) за принципами Гексагональної архітектури (ЛР 2) та використання окремої моделі читання (кешування статусів).
*   **Виявлений ризик:** Видача клієнту застарілого статусу ремонту (Stale Data) у проміжку між генерацією доменної події `RepairOrderCompletedEvent` та оновленням кешу.
*   **Чутливий параметр (Sensitivity Point):** Час життя кешу (TTL) та затримка доставки доменних подій.
*   **Точка компромісу (Trade-off):** *Швидкодія (Performance) проти Строгої узгодженості (Strict Consistency)*. Зменшення навантаження на базу даних досягається за рахунок переходу до узгодженості в кінцевому рахунку (Eventual Consistency).

## 2. Альтернативи та критерії порівняння

Для цільового розгортання системи розглянуто 3 конфігурації:
1. **Альтернатива A (Базовий Моноліт):** Усі компоненти розгорнуто як єдиний процес на одному VPS з локальною БД PostgreSQL (без брокерів повідомлень).
2. **Альтернатива B (Модульний моноліт + PaaS/Черги):** Чітке розділення доменів, розгортання на Managed PaaS із виділеним Redis/RabbitMQ для надійної роботи Saga та фонових воркерів.
3. **Альтернатива C (Мікросервіси на Kubernetes):** Повна фізична ізоляція `RepairService` та `WarehouseService` у контейнерах з власними БД (Database-per-service).

### Вихідні показники (синтетичні та довідкові дані)

| Альтернатива | Вартість ($/міс) *(min, синтет.)* | Час обробки (мс) *(min, синтет.)* | Відмовостійкість SLA (%) *(max, довідк.)* | Складність підтримки (1-10) *(min, синтет.)* |
| :--- | :---: | :---: | :---: | :---: |
| **A (Базовий Моноліт)** | 50 | 300 | 99.00 | 3 |
| **B (Модульний + PaaS)** | 150 | 200 | 99.90 | 6 |
| **C (Мікросервіси K8s)** | 500 | 150 | 99.99 | 9 |

## 3. Багатометрикове оцінювання та розрахунок втрат

Для приведення показників до єдиної шкали $[0; 1]$ використано формули нормованих втрат:
* Для критеріїв мінімізації: $L = \frac{value - min}{max - min}$
* Для критеріїв максимізації: $L = \frac{max - value}{max - min}$

Автоматизацію обчислень реалізовано у скрипті [`scripts/evaluate_architecture.py`](../scripts/evaluate_architecture.py).

### Матриця нормованих втрат

| Альтернатива | $L_{\text{Cost}}$ | $L_{\text{Latency}}$ | $L_{\text{SLA}}$ | $L_{\text{Complexity}}$ |
| :--- | :---: | :---: | :---: | :---: |
| **A (Базовий Моноліт)** | 0.00 | 1.00 | 1.00 | 0.00 |
| **B (Модульний + PaaS)** | 0.22 | 0.33 | 0.09 | 0.50 |
| **C (Мікросервіси K8s)** | 1.00 | 0.00 | 0.00 | 1.00 |

### Інтегральна оцінка $J$ (менше значення = кращий вибір)

1. **Набір ваг 1 — Пріоритет бюджету та простоти (Стартап):**  
   $W_1 = \{ \text{Cost}: 0.5, \text{Latency}: 0.1, \text{SLA}: 0.1, \text{Complexity}: 0.3 \}$
   * $J(A) = 0.00\cdot0.5 + 1.00\cdot0.1 + 1.00\cdot0.1 + 0.00\cdot0.3 = \mathbf{0.20}$ *(Переможець)*
   * $J(B) = 0.22\cdot0.5 + 0.33\cdot0.1 + 0.09\cdot0.1 + 0.50\cdot0.3 = \mathbf{0.30}$
   * $J(C) = 1.00\cdot0.5 + 0.00\cdot0.1 + 0.00\cdot0.1 + 1.00\cdot0.3 = \mathbf{0.80}$

2. **Набір ваг 2 — Пріоритет надійності та швидкодії (Зростання навантаження):**  
   $W_2 = \{ \text{Cost}: 0.1, \text{Latency}: 0.3, \text{SLA}: 0.5, \text{Complexity}: 0.1 \}$
   * $J(A) = 0.00\cdot0.1 + 1.00\cdot0.3 + 1.00\cdot0.5 + 0.00\cdot0.1 = \mathbf{0.80}$
   * $J(B) = 0.22\cdot0.1 + 0.33\cdot0.3 + 0.09\cdot0.5 + 0.50\cdot0.1 = \mathbf{0.22}$
   * $J(C) = 1.00\cdot0.1 + 0.00\cdot0.3 + 0.00\cdot0.5 + 1.00\cdot0.1 = \mathbf{0.20}$ *(Переможець)*

**Аналіз зміни вибору:** При зміні пріоритетів із жорсткої економії на забезпечення високого SLA вибір змінюється з найдешевшого моноліту (A) на розподілені конфігурації (C та B). При цьому Альтернатива B показує майже ідентичний результат до C ($0.22$ проти $0.20$).

## 4. Зіставлення вигод, витрат та припущень (CBAM)

* **Припущення:** Розрахункові показники вартості та затримок є синтетичними оцінками для базового навантаження сервісного центру (до 1000 заявок/добу) і не є офіційними тарифами хмарних провайдерів.
* **Аналіз доцільності:** Перехід до Альтернативи C (Kubernetes) дає приріст SLA лише на $0.09\%$ порівняно з Альтернативою B, але збільшує витрати на інфраструктуру більш ніж у 3 рази ($500 проти $150) і вимагає залучення виділеного DevOps-інженера (складність 9/10).
* **Оптимальне рішення:** **Альтернатива B (Модульний моноліт + PaaS/Черги)** забезпечує найкраще співвідношення вигод і витрат, надаючи необхідну інфраструктуру для надійної роботи Saga (черги повідомлень) без надлишкової складності мікросервісів.

### Висновок
Під час виконання лабораторної роботи №4 було проведено аналіз архітектурних ризиків і компромісів системи **TechRepair Hub** за мотивами методології ATAM. За допомогою багатометрикового оцінювання та нормування втрат порівняно три варіанти розгортання за різних бізнес-пріоритетів. На основі аналізу вигод і витрат (CBAM) обґрунтовано вибір модульного моноліту на Managed PaaS із чергами повідомлень та оформлено підсумковий ADR 002.
