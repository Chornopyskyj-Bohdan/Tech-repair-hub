# ADR 006: Політика автентифікації та контролю доступу на рівні ролей і об'єктів (JWT + RBAC + Object Ownership)

**Статус:** Прийнято  
**Дата:** 2026-11-24  
**Зіставлення з ADR першого модуля:** Доповнює [`ADR 001 (Гексагональна архітектура)`](./001-architectural-style.md) та [`ADR 003 (REST API)`](./003-api-style.md) без порушення незалежності доменного ядра.

## Контекст
У системі **TechRepair Hub** операції створення, читання, оновлення статусу та анулювання заявок на ремонт потребують розмежування прав між звичайними інженерами (`technician`) та керівником сервісного центру (`supervisor`). Крім ролі, необхідно захистити заявки від несанкціонованого доступу або зміни іншим інженером підміною `order_id` у URL (захист від BOLA/IDOR).

## Розглянуті альтернативи
1. **Перевірка доступу виключно на рівні API Gateway:**
   * *Плюси:* Централізація правил в одному місці.
   * *Мінуси:* Шлюз не володіє інформацією про власника конкретної заявки (`owner_id`) у сховищі сервісу ремонту. Крім того, внутрішній сервіс залишався б незахищеним у разі прямого звернення всередині периметра.
2. **Непрозорі сесійні токени з централізованою БД сесій:**
   * *Плюси:* Миттєве відкликання сесії.
   * *Мінуси:* Потребує додаткового мережевого запиту до сховища сесій при кожному виклику API, що суперечить локальній автономності та мінімальній затримці.
3. **Самодостатні підписані JWT (RFC 7519 / RFC 8725) + авторизація у власнику даних (`RepairOrder API`):**
   * *Плюси:* Сувора криптографічна перевірка алгоритму (`HS256`), підпису, `iss`, `aud` та `exp` бібліотекою `PyJWT`; отримання ідентифікатора суб'єкта `sub` і ролі `role` лише з верифікованого токена; перевірка володіння об'єктом (`owner_id == token.sub`) безпосередньо в компоненті, який керує заявками.

## Рішення
Ми обираємо **третій варіант**:
* Криптографічна верифікація JWT-токена та перевірка прав на конкретний ресурс (`_assert_order_access`) виконуються безпосередньо в `RepairOrder API` (`src/api/auth.py`, `src/api/app.py`).
* Секретний ключ підпису не зберігається в Git — він передається через змінну середовища `TECHREPAIR_JWT_SECRET` або генерується ефемерно в пам'яті (`secrets.token_urlsafe(32)`).
* Відсутній або невалідний токен повертає `401 Unauthorized`; спроба виконати операцію недозволеною роллю або над чужим об'єктом повертає `403 Forbidden` без зміни стану сховища.

## Наслідки та умова перегляду
* **Позитивні:** Усунуто вразливість підміни ідентифікатора об'єкта між користувачами з однаковою роллю (`tech-alice` та `tech-bob`); доменний агрегат `RepairOrder` залишається чистим від HTTP/JWT-залежностей.
* **Умова перегляду:** При переході до промислової багатосервісної експлуатації локальний симетричний емітент (`HS256`) має бути замінений на зовнішній OIDC-провайдер із асиметричними ключами (`RS256` / JWKS) та обов'язковим TLS.
