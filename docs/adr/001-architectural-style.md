# ADR 001: Вибір архітектурного стилю Модульного моноліту для системи TechRepair Hub

* **Статус:** Прийнято (Accepted)
* **Дата:** 2026-11-10
* **Автори:** Чорнописький Богдан (Архітектор проєкту)
* **Тег:** #architecture #style #modular-monolith #decisions

## 1. Контекст та постановка проблеми
Ми розробляємо нову систему керування ремонтом комп'ютерної техніки (TechRepair Hub). Система повинна підтримувати облік заяв, діагностику, управління складом запчастин, фінанси та надсилання сповіщень.

На початковому етапі розробки вимоги до системи можуть змінюватися, розмір команди розробки є невеликим (1–3 особи), а бюджет на інфраструктуру — обмеженим. Необхідно обрати архітектурний стиль, який забезпечить швидкий Time-to-Market, просте відлагодження, але при цьому залишить можливість легкого проведення декомпозиції в майбутньому.

## 2. Розглянуті варіанти
1. **Класичний моноліт (Monolithic Architecture):** Єдиний код без чіткого поділу на внутрішні модулі.
2. **Мікросервісна архітектура (Microservices Architecture):** Поділ системи на 4–6 автономно розгортаних мікросервісів з окремими БД.
3. **Модульний моноліт (Modular Monolith Architecture):** Єдиний застосунок для розгортання, розділений на чіткі незалежні бізнес-модулі з суворо визначеними межами та інтерфейсами (DDD Bounded Contexts).

## 3. Прийняте рішення
**Обране рішення:** **Варіант 3 — Модульний моноліт (Modular Monolith).**

Ми розгортаємо єдиний процес сервера (Core API), але всередині коду суворо дотримуємося модульної структури за принципами Domain-Driven Design (DDD):
- Модуль `RepairManagement`
- Модуль `WarehouseManagement`
- Модуль `BillingAndFiscal`
- Модуль `NotificationService`

Прямі виклики між модулями дозволені лише через публічні доменні інтерфейси (Contract APIs), а міжмодульна взаємодія для некритичних за часом задач відбувається через внутрішньопроцесну шину подій (In-Memory Event Bus).

### Обґрунтування:
- **Мінімізація випадкової складності:** Відсутність потреби у складній інфраструктурі (Kubernetes, Service Mesh) на ранньому етапі.
- **Збереження ACID-транзакційності:** Списання запчастини зі складу та зміна статусу заявки відбуваються в межах однієї БД без потреби реалізовувати складний патерн Saga.
- **Готовність до мікросервісів у майбутньому:** Чітко визначені межі модулів (Bounded Contexts) дозволять за потреби легко винести будь-який модуль у окремий мікросервіс.

## 4. Наслідки рішення

### Позитивні наслідки (+):
* Висока швидкість розробки та простота тестування (достатньо підняти одну базу даних і один сервер).
* Низька вартість інфраструктури (достатньо одного стандартного VPS / Docker-контейнера).
* Проста підтримка цілісності даних завдяки SQL-транзакціям.

### Негативні наслідки (-):
* Ризик поступової деградації архітектури в "Big Ball of Mud", якщо розробники порушуватимуть межі модулів.
* Масштабування можливе лише всієї системи цілком.

## 5. Умови перегляду рішення
Це рішення підлягає перегляду та потенційному переходу на мікросервіси за наступних умов:
1. **Зростання команди:** Кількість розробників перевищить 15 осіб.
2. **Нерівномірне навантаження:** Модуль сповіщень чи клієнтського відстеження зазнаватиме високого навантаження (понад 10,000 RPS).
3. **Вимоги до незалежного релізного циклу:** Бізнес вимагатиме оновлювати окремий модуль по кілька разів на день незалежно від ядра.
