# ADR 007: Уточнення інфраструктурної та інтеграційної архітектури за результатами оцінки (ЛР 5–8)

**Статус:** Прийнято (уточнює та замінює положення [`ADR 002`](./002-infrastructure-config.md) щодо локального розгортання та міжкомпонентної взаємодії)  
**Дата:** 2026-11-24

## Контекст
У першому модулі (`ADR 002`) було прийнято рішення про монолітне розгортання всього застосунку в одному процесі без зовнішніх брокерів та проміжних проксі для мінімізації складності. Під час реалізації та експериментального оцінювання у ЛР 5–8 виявилося, що:
1. Синхронна обробка зовнішніх залежностей (перевірка гарантії виробника) та фінансового обліку створює ризик каскадних відмов при затримках або збоях.
2. Загальна швидкість реакції при деградації зовнішнього сервісу без запобіжника становить ~130 мс на кожен невдалий запит із 100% навантаженням на збійний вузол.

## Розглянуті альтернативи
1. **Зберегти суворий моноліт з `ADR 002` без брокера і шлюзу:** не дозволяє ізолювати збої зовнішніх сервісів та гарантувати доставку подій після перезапуску споживача.
2. **Повний перехід на розподілені мікросервіси з Kubernetes та Kafka:** надмірна операційна складність для масштабу сервісного центру.
3. **Модульний моноліт із виділеним API Gateway, асинхронним брокером RabbitMQ та гексагональним ядром:** зберігає єдине доменне ядро, але виносить політики стійкості на межу шлюзу (`ADR 005`), фонову фінансову аналітику — в ідемпотентного споживача RabbitMQ (`ADR 004`), а контроль доступу JWT/RBAC — у шар REST API (`ADR 006`).

## Рішення
Ми **уточнюємо `ADR 002`** (позначаючи його однопроцесну конфігурацію як базову лише для доменного ядра, замінену новою топологією для інтеграційного контуру):
* Залишити доменне ядро (`src/domain/`) повністю ізольованим від фреймворків та брокерів.
* Використовувати комбіновану топологію: **API Gateway** (маршрутизація, Rate Limiting, Deadline, Retry, Circuit Breaker) $\rightarrow$ **RepairOrder API** (JWT-верифікація, RBAC, володіння об'єктами) + **RabbitMQ** (асинхронна публікація `RepairOrderCompleted` для ідемпотентного споживача SQLite).

## Наслідки та умова перегляду
* **Позитивні:** Підтверджено експериментами у ЛР 6–8: 0 дублікатів при повторній доставці повідомлень, зниження викликів до збійної залежності на 70% (з 30 до 9 у серії тестів) та 100% блокування несанкціонованого доступу до чужих заявок (`401`/`403`).
* **Умова перегляду:** Якщо навантаження перевищить пропускну здатність одного екземпляра `RepairOrder API` або знадобиться повне повторне програвання історії подій (Event Replay), слід переглянути вибір брокера (`ADR 004`) на користь Apache Kafka та виділити сервіс споживача в окремий контейнер.
