# ADR 002: Вибір конфігурації розгортання та архітектури (Багатометриковий вибір)

**Статус:** Прийнято  
**Дата:** 2026-11-13  
**Контекст:**  
Система TechRepair Hub потребує визначення цільової конфігурації інфраструктури. Нам необхідно забезпечити виконання вимог з відмовостійкості (SLA), продуктивності, та зберегти складність підтримки в розумних межах. У ЛР3 було впроваджено патерн Saga, що вимагає надійних черг для компенсацій.

## Альтернативи
1. **A (Базовий Моноліт):** Усе в одному процесі, 1 БД. (Дешево, просто, але слабка відмовостійкість).
2. **B (Модульний моноліт на Managed PaaS з чергами):** Розділення доменів, використання Managed Redis/RabbitMQ для Saga. (Збалансовано).
3. **C (Мікросервіси на Kubernetes):** Повна ізоляція сервісів, database-per-service. (Дорого, складно, максимальний SLA).

## Оцінка (За методологією мінімізації втрат)
Було застосовано два набори ваг:
*   *Сценарій 1 (Бюджет і Простота):* Cost (0.5), Latency (0.1), SLA (0.1), Complexity (0.3). Найменші втрати показала Альтернатива A (J=0.20).
*   *Сценарій 2 (Надійність і Продуктивність):* Cost (0.1), Latency (0.3), SLA (0.5), Complexity (0.1). Найменші втрати у Альтернативи C (J=0.20) та B (J=0.21).

## Рішення
Ми обираємо **Альтернативу B (Модульний моноліт на Managed PaaS з чергами)**.

**Обґрунтування:**
Незважаючи на те, що за сценарієм 2 Альтернатива C має незначну перевагу в J-оцінці, витрати на розгортання Kubernetes (Cost = 500) та складність (Complexity = 9) не виправдані для поточної бізнес-моделі TechRepair Hub (відповідно до аналізу CBAM). Альтернатива B забезпечує SLA 99.9%, що достатньо для нашого сценарію, та надає інфраструктуру для надійної обробки Saga-компенсацій.

## Наслідки (Ризики та Компроміси)
*   **Позитивні:** Значне підвищення відмовостійкості порівняно з базовим монолітом; можливість незалежного масштабування фонових воркерів.
*   **Негативні:** Зростання щомісячних витрат на інфраструктуру в 3 рази; необхідність адміністрування черг (Redis/RabbitMQ).
*   **Умови перегляду:** Якщо навантаження зросте до понад 5000 транзакцій на секунду, або команди розробки Warehouse та Repair Service будуть налічувати більше 20 осіб кожна, рішення буде переглянуто на користь мікросервісів (Альтернатива C).
