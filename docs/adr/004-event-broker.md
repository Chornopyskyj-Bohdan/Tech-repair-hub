# ADR 004: Вибір брокера повідомлень та забезпечення надійності публікації (RabbitMQ vs Kafka)

**Статус:** Прийнято  
**Дата:** 2026-11-24  
**Контекст:**  
У системі **TechRepair Hub** після завершення ремонту (`RepairOrderCompleted`) необхідно асинхронно передавати дані до модуля фінансового обліку та аналітики (`BillingAnalyticsConsumer`), не блокуючи роботу основного сервісу ремонту та зберігаючи незалежність доменного ядра.

## Порівняння RabbitMQ та Apache Kafka для нашого сценарію

| Критерій | RabbitMQ (AMQP 0-9-1) | Apache Kafka (Distributed Log) |
| :--- | :--- | :--- |
| **Модель обробки** | Smart Broker / Dumb Consumer: маршрутизація через Exchanges, індивідуальні підтвердження (`ACK`/`NACK`) на кожне повідомлення. | Dumb Broker / Smart Consumer: незмінний журнал (log), споживач керує зсувом (`offset`) у партиціях. |
| **Маршрутизація помилок** | Вбудований механізм **Dead Letter Exchange (DLX)** автоматично відправляє пошкоджені повідомлення в чергу помилок (`DLQ`). | Немає вбудованого DLQ на рівні брокера — необхідно реалізовувати окремі топіки помилок на рівні споживача. |
| **Складність інфраструктури** | Низька: один легкий контейнер, мінімальне споживання пам'яті (відповідає ADR 002). | Висока: потребує кластерної конфігурації (KRaft/ZooKeeper), важчий у локальному розгортанні. |
| **Повторне програвання (Replay)** | Після `ACK` повідомлення видаляється з черги. | Зберігає історію подій за часом/обсягом (Retention Policy), дозволяє повторне читання з нуля. |

## Рішення
Ми обираємо **RabbitMQ** із налаштуваннями надійності (`durable` exchange/queue, `persistent` повідомлення `delivery_mode=2`, **Publisher Confirms**, ручний `basic_ack` після транзакції БД та **Dead Letter Queue**).

**Обґрунтування:**  
Для сервісного центру важливі надійна доставка завдань на обробку актів виконаних робіт, прозора ізоляція невалідних повідомлень через DLX/DLQ та низька операційна складність. Сценарій не потребує потокової аналітики мільйонів подій на секунду чи повного Event Sourcing, де переваги Kafka були б критичними.

## Ризик втрати події (Dual Write Problem) та Transactional Outbox
* **Проблема подвійного запису:** Коли `RepairService` зберігає стан заявки `COMPLETED` у своїй БД, а потім окремим мережевим викликом публікує подію в RabbitMQ, існує вікно вразливості: якщо процес впаде між комітом у БД та отриманням Publisher Confirm від брокера, заявка в БД буде завершена, а подія в чергу ніколи не потрапить.
* **Рішення (Transactional Outbox):** У промисловій експлуатації застосовується патерн *Transactional Outbox*. У межах тієї самої локальної транзакції БД, де оновлюється `RepairOrder`, у спеціальну таблицю `outbox_messages` записується серіалізована подія `RepairOrderCompleted`. Окремий фоновий процес (Message Relay) вичитує необроблені записи з `outbox_messages`, публікує їх у RabbitMQ і після отримання `Publisher Confirm` позначає їх як відправлені. У поєднанні з ідемпотентним споживачем це гарантує доставку *at-least-once* без втрат даних.
