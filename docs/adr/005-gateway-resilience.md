# ADR 005: Баланс між швидкою відмовою, навантаженням та шансом відновлення на API Gateway

**Статус:** Прийнято  
**Дата:** 2026-11-24  
**Контекст:**  
У системі **TechRepair Hub** шлюз (`API Gateway`) маршрутизує зовнішні запити до основного сервісу заявок (`RepairOrder API`) та зовнішньої залежності перевірки гарантії виробника (`VendorWarrantyService`). При деградації або зависанні зовнішнього сервісу виникає ризик каскадних відмов, вичерпання потоків клієнтів та «шторму повторів» (*Thundering Herd*).

## Розглянуті компроміси

1. **Агресивні повтори без обмежень (Високий шанс відновлення $\rightarrow$ критичне навантаження):**
   * *Плюси:* Максимальна ймовірність отримати успішну відповідь при короткочасних мережевих збоях.
   * *Мінуси:* Потроює/помножує трафік на вже перевантажену залежність, збільшує час очікування клієнта та спричиняє каскадне зависання.
2. **Миттєва відмова без повторів (Мінімальне навантаження $\rightarrow$ втрата запитів при одиничних збоях):**
   * *Плюси:* Мінімальна затримка (Fast Fail) і нульове додаткове навантаження на залежність.
   * *Мінуси:* Будь-який одноразовий мережевий пакетний збій або короткий рестарт сервісу призводить до помилки для користувача.
3. **Комбінований захист (Timeout + Deadline + Bounded Retry з Backoff/Jitter + Circuit Breaker + Rate Limiting):**
   * Обмежені повтори (до 3 спроб) із *Exponential Backoff + Jitter* застосовуються **виключно** до безпечних операцій читання (`GET`) при тимчасових збоях (`502`, `503`, `504`, `TimeoutException`), не перевищуючи загальний бюджет часу (`overall_deadline`).
   * Якщо збій триває довше (`failure_threshold = 3`), спрацьовує **Circuit Breaker** (`OPEN`), який припиняє навантажувати залежність і повертає миттєву відмову (*Fast Fail*), а через `recovery_timeout` перевіряє відновлення в режимі `HALF_OPEN`.

## Рішення

Ми приймаємо **комбіновану стратегію захисту** з такими параметрами для читання гарантії:
* `per_attempt_timeout = 0.15s` (на локальному стенді; `0.20s` у базовому профілі) та `overall_deadline = 0.45s` (`0.65s` у базовому профілі).
* `max_attempts = 3`, `base_backoff = 0.04s`, `max_jitter = 0.02s`.
* `Circuit Breaker`: `failure_threshold = 3`, `recovery_timeout = 0.4s` (на стенді; `1.0s` у базовому профілі), `half_open_max_calls = 1`.
* `Rate Limiting`: алгоритм *Fixed Window* за ключем `X-Client-ID` із відповіддю `429 Too Many Requests` та заголовком `Retry-After`.
* **Операції зміни стану (`POST`, `PATCH`):** автоматичні повтори вимкнені (`max_attempts = 1`), оскільки мережевий таймаут не гарантує, що запис не відбувся, а повтор без ключа ідемпотентності створить дублікат заявки.

## Наслідки
* **Позитивні:** Короткі збої (1–2 невдалі спроби) прозоро маскуються ретраями; при тривалій аварії залежності навантаження на неї падає до нуля після відкриття `Circuit Breaker`, а час відгуку шлюзу скорочується з сотень мілісекунд до `< 5 мс`.
* **Обмеження:** У стані `OPEN` нові запити відхиляються до завершення `recovery_timeout`, навіть якщо зовнішній сервіс відновився на кілька сотень мілісекунд раніше.
