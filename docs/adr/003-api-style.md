# ADR 003: Вибір стилю API для інтеграції компонентів (REST vs gRPC vs GraphQL)

**Статус:** Прийнято  
**Дата:** 2026-11-24  
**Контекст:**  
Для системи **TechRepair Hub** необхідно відкрити програмний інтерфейс керування заявками на ремонт (`RepairOrder`), щоб відокремити транспортний рівень від доменного ядра (ЛР 2) та заборонити зовнішнім клієнтам прямий доступ до сховища.

## Вимоги системи до API
1. **Простота інтеграції та кешування читання:** Клієнти (веб-інтерфейс, сканер QR-кодів статусу) часто читають статус заявок за ID; потрібна стандартна підтримка HTTP-кешування та прозора документація (OpenAPI).
2. **Помірна складність супроводу:** Відповідно до ADR 002 (модульний моноліт на PaaS), команда невелика, тому транспортний шар не повинен вимагати складної кодогенерації чи окремої інфраструктури.

## Порівняння альтернатив

| Критерій | REST (HTTP/JSON + OpenAPI) | gRPC (HTTP/2 + Protobuf) | GraphQL (SDL) |
| :--- | :--- | :--- | :--- |
| **Інтеграція та кешування** | Висока: нативне HTTP-кешування для `GET`, зрозумілі статус-коди (`201`, `404`, `409`), OpenAPI 3.1. | Низька для браузерів: потребує gRPC-Web проксі, немає стандартного HTTP-кешування. | Середня: усе йде через `POST`, що ускладнює мережеве кешування. |
| **Складність супроводу** | Низька: стандартні інструменти (FastAPI, httpx), легке налагодження. | Середня/Висока: управління `.proto`-схемами та кодогенерація. | Висока: потреба в резолверах та захисті від проблеми N+1 (DataLoader). |

## Рішення
Ми обираємо **REST API (рівень 2 моделі Річардсона)** із описом контракту в **OpenAPI 3.1.1**.

## Обґрунтування вибору методів та статус-кодів
* `POST /api/v1/repair-orders` $\rightarrow$ **`201 Created`**: створює новий ресурс і повертає його представлення.
* `GET /api/v1/repair-orders/{order_id}` $\rightarrow$ **`200 OK`** або **`404 Not Found`**: безпечна ідемпотентна операція читання, придатна для кешування.
* `PATCH /api/v1/repair-orders/{order_id}/status` $\rightarrow$ **`200 OK`**, **`409 Conflict`** (порушення інваріантів переходу станів), **`422 Unprocessable Entity`** (помилка валідації даних).

## Наслідки та умови перегляду
* **Позитивні:** Швидкий старт, сумісність з будь-якими клієнтами, просте контрактне тестування.
* **Негативні:** Можливий надлишковий обсяг даних (Over-fetching) при розширенні моделі заявки.
* **Умови перегляду:** Якщо з'являться високонавантажені внутрішні міжсервісні виклики (East-West) із жорсткими вимогами до затримок, для них буде розглянуто **gRPC**.
