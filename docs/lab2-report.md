## 1. Стратегічний DDD (Domain-Driven Design)

Для системи TechRepair Hub було визначено ключові піддомени та обмежені контексти (Bounded Contexts).

### 1.1. Піддомени та Обмежені Контексти
1. **Core Domain (Доменне ядро): `Repair Management` (Управління ремонтом)**  
   Головний бізнес-контекст, що забезпечує основну цінність. Відповідає за прийом техніки, діагностику, узгодження вартості з клієнтом, контроль статусу ремонту та його завершення.  
   *Взаємодія:* Виступає джерелом подій для інших контекстів (наприклад, генерує подію про завершення ремонту).
2. **Supporting Subdomain (Допоміжний): `Warehouse` (Склад)**  
   Допоміжний контекст для управління запчастинами, списання деталей та контролю залишків.  
   *Взаємодія:* Реагує на події від `Repair Management` (наприклад, резервує запчастини під час узгодження кошторису).
3. **Generic Subdomain (Загальний): `Billing` (Біллінг/Оплата)**  
   Стандартний контекст для формування рахунків та обробки платежів (може бути замінений готовим рішенням).  
   *Взаємодія:* Реагує на подію успішного ремонту та виставляє фінальний рахунок.

### 1.2. Ubiquitous Language (Словник термінів)
1. **Repair Order (Заявка на ремонт):** Головний агрегат системи, що відстежує життєвий цикл ремонту.
2. **Device Specification (Специфікація пристрою):** Деталі пристрою, який ремонтується (бренд, модель, серійний номер).
3. **Money (Гроші):** Точне представлення фінансової вартості (сума та валюта) для уникнення помилок заокруглення.
4. **Diagnostic (Діагностика):** Процес виявлення несправностей та визначення вартості робіт.
5. **Estimated Cost (Кошторис):** Попередня вартість ремонту, визначена після діагностики, яка потребує узгодження.
6. **Repair Status (Статус ремонту):** Поточний етап життєвого циклу заявки (NEW, IN_DIAGNOSTICS, WAITING_FOR_APPROVAL, IN_PROGRESS, COMPLETED, CANCELLED).
7. **Business Invariant (Бізнес-інваріант):** Суворе бізнес-правило, яке ніколи не може бути порушене (наприклад, заборона початку ремонту без діагностики).
8. **Repair Order Completed Event (Подія завершення ремонту):** Доменна подія, що сигналізує про готовність пристрою.

## 2. Тактичний DDD та Доменне ядро (Завдання 2)

У рамках лабораторної роботи реалізовано доменне ядро у папці `src/domain/`.

*   **Агрегат:** `RepairOrder` — керує станом заявки, контролює інваріанти та генерує події.
*   **Об'єкти-значення (Value Objects):**
    *   `Money` — гарантує, що сума не може бути від'ємною і не дозволяє додавати різні валюти.
    *   `DeviceSpecification` — гарантує, що пристрій не може бути створений без серійного номера.
*   **Доменна подія:** `RepairOrderCompletedEvent` — фіксує факт успішного ремонту.

### 2.1. Бізнес-інваріанти та переходи стану
1.  **Інваріант 1:** Неможливо розпочати ремонт (перехід у стан `IN_PROGRESS`), якщо не було проведено діагностику та не узгоджено кошторис (`estimated_cost`). При порушенні викидається `DiagnosticRequiredException`.
2.  **Інваріант 2:** Завершити ремонт (перехід у стан `COMPLETED`) можна лише тоді, коли заявка перебуває у стані виконання (`IN_PROGRESS`). При порушенні викидається `InvalidStateTransitionException`.

## 3. Чиста Архітектура (Завдання 3)

Застосовано принцип інверсії залежностей (Гексагональна архітектура):
*   **Порт:** У доменному ядрі створено абстрактний інтерфейс `IRepairOrderRepository` (`src/domain/repository_port.py`), який визначає контракти `save` та `get_by_id`. Ядро нічого не знає про бази даних.
*   **Адаптер:** В інфраструктурному шарі реалізовано `InMemoryRepairOrderRepository` (`src/infrastructure/in_memory_repository.py`), який зберігає агрегати у словнику (у пам'яті) і реалізує інтерфейс порту.

## 4. Модульне тестування (Завдання 4)

У папці `tests/` створено файл `test_repair_order.py` з використанням фреймворку `pytest`.
Тести повністю ізольовані та успішно покривають наступні сценарії:
1.  Коректне створення агрегату `RepairOrder`.
2.  Спрацювання валідації Value Object (помилка при порожньому серійному номері `DeviceSpecification`).
3.  Спрацювання валідації Value Object (виняток `InvalidMoneyAmountException` при від'ємній сумі грошей).
4.  Порушення інваріанта (помилка при спробі почати ремонт без діагностики).
5.  Повний життєвий цикл (дозволені переходи станів від `NEW` до `COMPLETED` та генерація події `RepairOrderCompletedEvent`).
6.  Збереження та отримання агрегату через інфраструктурний адаптер (In-Memory репозиторій).
